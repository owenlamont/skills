# Python Lint & Format (prek)

This project runs its linters and formatters through
[prek](https://github.com/j178/prek), a pre-commit-compatible hook runner. The hooks
cover Python style/typing as well as Markdown, YAML, and spelling.

## Installing the git hooks

A clone does not install prek's hooks — each developer installs them, and forgetting on
a fresh clone silently skips the checks:

```bash
prek install --install-hooks --overwrite
```

This is idempotent: re-run it if commits complete without the checks running. It needs a
`prek.toml` or `.pre-commit-config.yaml` present (the `--install-hooks` step also prepares
each hook's environment).

To verify the hooks are installed — cross-platform, via uv/Python rather than
shell-specific `grep`/`Select-String` (the shim's header reads `# File generated by
prek`):

```bash
uv run python -c "import pathlib, subprocess; p = pathlib.Path(subprocess.run(['git', 'rev-parse', '--git-path', 'hooks'], capture_output=True, text=True).stdout.strip(), 'pre-commit'); print('installed' if p.is_file() and 'generated by prek' in p.read_text() else 'not installed')"
```

## Running prek

```bash
prek run --all-files
```

- It auto-fixes many issues; if a run reports changed files, run it again (some first-run
  failures are already fixed).
- Fix issues by hand only when a run reports no file changes but still fails.
- It only scans git-tracked files — `git add` new files first.

## What the toolchain enforces

Each hook is driven by a config file at the repo root:

| Config file        | Tool       | Enforces                |
| ------------------ | ---------- | ----------------------- |
| `ruff.toml`        | Ruff       | Code style and linting  |
| `ty.toml`          | ty         | Static type checking    |
| `.complexipy.toml` | complexipy | Code complexity limits  |
| `.rumdl.toml`      | rumdl      | Markdown linting        |
| `.ryl.toml`        | ryl        | YAML linting            |
| `typos.toml`       | typos      | Spelling                |
| `biome.json`       | Biome      | JS/TS/JSON linting      |

**Lines wrap at 88 characters, and that applies to Markdown prose as well as Python.**
Ruff enforces it on code (`ruff.toml`) and rumdl enforces it on every `.md` file
(`.rumdl.toml`, rule `MD013`) — so a hand-wrapped paragraph at 89 characters fails the
hooks much like an over-long line of code, subject to the one exemption described below.
Wrap prose as you write it rather than discovering it on the first failed run.

**`ruff` takes `target-version` from the project's `requires-python`, and ignores a
standalone script's own PEP 723 block.** A script pinned below the project's floor is
therefore rewritten with syntax it cannot run, by the formatter and by a version-gated
lint fix alike, and the hand fix is undone on every run. Measured on ruff 0.16.7 in a
project declaring `>=3.14`: `except (OSError, ValueError):` was rewritten to the
3.14-only `except OSError, ValueError:` both with and without a
`requires-python = "==3.13.*"` block in the script, while the same file outside any
project was left alone. `uv run --script` *does* honour the block, so the script then
fails with `SyntaxError: multiple exception types must be parenthesized`. The same
override reached `ruff check --fix`, where `UP045` rewrote against the project's target
past a script pinned at `==3.9.*`. Where a script has to stay below the project's floor,
scope the override to it with a `[per-file-target-version]` entry in `ruff.toml` — a bare
`target-version` would drop the whole tree to that floor. Measured on the same probe:
with `"legacy.py" = "py313"`, the pinned file kept its parentheses while the file beside
it was still rewritten.

Check the files you just edited without waiting for a full hook run — from the repo root,
so the tool picks up the repo's config:

```bash
rumdl check path/to/file.md    # markdown only, milliseconds; --fix applies what it can
ruff check path/to/file.py     # add --fix to apply what it can
```

Both hooks run `--fix` in the gate, so a fixable violation is one the gate would have
rewritten anyway — applying it here just saves the round trip. `MD013` is not among them:
no tool reflows a paragraph, which is why the wrapping rule above is yours to keep.

Scope it to the paths you touched. `prek run --all-files` stays the gate before you commit;
these are for the edit-by-edit loop, where a full run's cost discourages checking at all.

**Which lines are exempt is a per-repo setting, so read the repo's own `.rumdl.toml`
before concluding a long line is fine.** Four keys decide it — `code_blocks`, `tables`,
`headings` and `strict` — and a repo that exempts tables (`tables = false`) accepts a
wide table cell that fails in one that doesn't.

Two `MD013` exemptions worth knowing before you conclude a long line is fine. YAML
frontmatter is skipped entirely, so a 300-character skill `description:` passes while
the same sentence in the body fails at 89. And `strict = false` exempts any line that no
break could bring inside the limit — which is a *positional* test, not "the line is one
long token". Measured against a `line_length = 88` config: a line passes when there is
no space after column 88, so ordinary prose whose final word straddles the limit is
accepted at 89–91 characters, while a 92-character line with a space at column 89 fails.
A bare URL is only the extreme case, and a deliberately over-long test line made of one
unbroken word therefore proves nothing about whether the check works.

Three consequences worth having before you start editing. Don't fix a flagged line by
moving one word onto the next line: that relocates the break point and can push a
neighbouring line that was legitimately exempt over the edge — reflow the whole paragraph
instead, and don't "fix" an 89–91 character line the hooks already accept. Run
`rumdl check <file>` rather than counting characters, because length alone does not
predict the verdict. And keep a `repo#123` reference whole on one line: a reflow that
lands `#123` at the start of a line makes it a heading, which `rumdl` fails as `MD018` —
auto-fixable, and the fix inserts the space, turning the reference into a real heading
rather than restoring it.

`MD013` counts **characters**, not bytes: a 33-character line of em dashes measuring 93
bytes passes, while a 91-character ASCII line fails only when its last space sits past
column 88 — the positional exemption above decides the rest. So don't count with `awk`.
`awk 'length > 88'` agrees only when the shell's locale is UTF-8 — under `LC_ALL=C`, or
with no locale set, GNU awk switches to bytes and every line carrying an em dash or a
curly quote reads two or three over. Prose here is full of both, so the check becomes
noise pointing at lines the hooks accept.

Reflow the flagged paragraph in **one pass** rather than nudging words across the break,
which relocates the break point and re-fails somewhere new — four rounds on one
paragraph, measured. `textwrap` counts characters, so it agrees with `MD013`; hold the
spaces inside code spans out of the wrap so none is split across a newline:

```python
HOLD = "\x00"
text = " ".join(paragraph.split())
text = re.sub(r"`[^`]*`", lambda m: m[0].replace(" ", HOLD), text)
text = re.sub(r"(\S) (#\d+)", rf"\1{HOLD}\2", text)
print(
    textwrap.fill(text, 88, break_long_words=False, break_on_hyphens=False).replace(
        HOLD, " "
    )
)
```

The second substitution is the `MD018` trap above, and it is not optional: without it a
wrap strands a bare `#123` at the start of a line — 2 of 40 paragraph lengths measured.
Re-run `rumdl check <file>` after either way: a code span longer than the width still
overflows, and that is the case to fix by hand.

## Wrapping Python docstrings and comments

`ruff` caps Python at the same 88 columns (`line-length` in `ruff.toml`, reported as
`E501`), and `ruff-format` rewraps **code only** — it will parenthesise a long
expression, but it never moves a line break inside a docstring, comment or string
literal. So one format pass can clear an overlong code line and leave the prose beside it
still failing.

Reflow that prose by hand, a whole paragraph at a time. Shortening a flagged docstring
line by moving one word onto the next relocates every later break point and pushes the
following line over instead — the same trap as Markdown, and it repeats down the
paragraph until some line has slack. `E501`'s exemptions are its own rather than
`MD013`'s: it spares a line carrying no whitespace past its indentation, and one ending
in a URL that starts before the cap, but it still fails a line whose only whitespace sits
early. Run `ruff check <file>` rather than counting columns.

## Keeping the hook pins current

No bot refreshes `prek.toml` in a personal repo, so the `rev` pins sit wherever they
were last set, and a stale linter does not announce itself as old: it surfaces as a
**false positive** on correct content, which reads as a problem with the file rather than
with the pin. The tell is a newer copy disagreeing — `uvx rumdl@<newer> check <file>`
passing what the pinned hook rejects, and `--fix` changing nothing. Run
`prek autoupdate` then `prek run --all-files` before contorting the prose around it, and
at any wrap-up where the repo was touched.

Ruff's own rules do not enforce the ban on runtime reflection that `python-code-style`
sets, so a green run is not evidence there is none left. Measured against a probe with
every rule enabled (`--select ALL --preview`), ruff 0.16 flags only the constant-attribute
forms — `B009` `getattr(x, "a")`, `B010` `setattr(x, "a", 1)`, and preview `B043`/`PLC2801`
for `delattr` and dunder calls — and nothing else: not `getattr(x, "a", default)`, not a
computed attribute name, not `hasattr`, `vars`, `globals`, `locals`, `__dict__`, `dir`,
3-argument `type("N", (), {})`, or `compile` (`eval` and `exec` are covered, by `S307` and
`S102`). Two configured hooks cover the rest between them, and which one reaches a given
form is not a matter of taste.

Which tool can ban a name at all turns on one question: **can that name be reached without
an import?** `TID251` matches an import, so `[lint.flake8-tidy-imports.banned-api]` is
blind to anything needing none; an `ast-grep` pattern matches source text, so it is blind
to any name an import renamed. Measured against ruff 0.16 with a `"builtins.getattr"`
entry, each form in its own file carrying its own import:

| How it is written | `ast-grep` | ruff `banned-api` |
| --- | --- | --- |
| `getattr(x, n)` bare | only tool | — nothing to match against |
| `builtins.getattr(x, n)` | yes | yes |
| `import builtins as b` → `b.getattr(x, n)` | — | only tool |
| `from builtins import getattr as g` → `g(x, n)` | — | only tool, at the import line |
| `from builtins import *` | yes | `UP029` + `F403` |
| `g = getattr` → `g(x, n)` | — | — |

So a **builtin** needs `ast-grep`, because it can be called with no import at all — that,
and only that, is what `banned-api` cannot express. A **non-builtin**
(`operator.attrgetter`, `importlib.import_module`, the reflective half of `inspect`) can
never be reached without an import, which makes `banned-api` not just sufficient but
*authoritative*: it fires at the import line whatever the name is aliased to afterwards,
so no downstream rename evades it. Banning a non-builtin in `ast-grep` alone puts it in
the one tool that cannot see its aliases.

Keep the qualified `builtins.$NAME(...)` pattern in `ast-grep` too, even though ruff
covers it — the overlap costs a few lines and catches a rebound *module*
(`import builtins as b; builtins = b; builtins.getattr(...)`), which ruff doesn't follow.

Neither tool resolves a rebind of the callable itself: `g = getattr; g(x, "a")` measured
zero hits from both, and closing it needs flow analysis neither does. Write that limit
down beside the rule rather than leaving it to be found — a gate documented as airtight
when it isn't is worse than one whose hole is stated.

Two more things a rule needs before you trust it as a gate:

- **Scan stubs, and test the rule itself.** Set `types_or = ["python", "pyi"]` or `.pyi`
  files go unscanned, and run the rule's own valid/invalid cases as a second hook
  (`ast-grep test`) pinning *both* sides of the line, so a rule that quietly stops
  matching fails the gate instead of going silent. Prove a new hook blocks a fresh
  violation end to end — add a violating file, stage it, watch it exit non-zero.
- **Make the probe carry whatever context the rule needs to fire.** A harness extracting
  one line into a file cannot test a `banned-api` entry at all, because `TID251` needs the
  import in the same file; one reported seven working bans as holes. "Zero hits" is
  evidence only once the harness is shown to produce a hit on a known-bad case.

## Resolving a failure

Work down this ladder. A suppression is the last resort, not the first response to a
warning:

1. **Fix the root cause** so the rule genuinely stops firing. Restructuring beats
   silencing: a Ruff `S608` on a dynamically built SQL string is better resolved by
   keeping the query text literal and binding the variable part (`json_each(?)` for a
   list of values) than by `# noqa: S608`.
2. **Scope a config-level ignore** when the exception is systemic rather than one line —
   a per-rule or per-path entry in `ruff.toml`, an entry in `typos.toml` (which knob is
   its own question — see *Scoping a `typos` exception*). Keep the scope as narrow as
   the real exception.
3. **Add an inline suppression** (`noqa`, `type: ignore`, a coverage `pragma`) only for
   a demonstrable false positive or a warning that isn't reasonably avoidable, with the
   justification `python-code-style` requires.

Never rewrite correct code — or correct prose, for a spelling hook — purely to appease a
false positive. A correctly spelled word that `typos` rejects is a `typos.toml` fix, not
a reworded sentence.

## Scoping a `typos` exception

`typos` flags *tokens*, not the words you wrote — it splits identifiers on case changes
and on hyphens — so **read which token it reported before choosing the knob**. Measured
on `typos` 1.49 against this line:

```text
Executed NDAs sit in the tree, and the mis-named arguments were flagged.
```

- `[default.extend-identifiers]` fixes a genuine whole identifier (`NDAs`). It cannot fix
  a hyphenated word: `mis-named` splits on the hyphen, so it is never an identifier and
  the entry never matches.
- `[default.extend-words]` is the wrong scope for a sub-word hit. `NDAs` is flagged as
  `ND`, so an `NDAs` entry does nothing — and an `ND` entry works but silences the
  `ND` → `AND` check everywhere.
- `extend-ignore-re` fixes both, and is the only one of the three that scopes a sub-word
  or hyphenated exception without disabling a check. Anchor each pattern:

  ```toml
  [default]
  extend-ignore-re = ["\\bNDAs\\b", "\\bmis-named\\b"]
  ```

  It is a `[default]` key. At the top level `typos` rejects the whole config with
  `unknown field`.

Confirm the scope with a control: after the exception, the genuine typos in the same file
must still fail. When probing a config, pass `--isolated` — `typos` otherwise merges any
`typos.toml` it discovers in the tree with the one given to `--config`, and the ambient
file quietly decides the result.
